# 日文校對工具（style-editor）

**繁體中文** | [English](README.en.md)

直接讀取 **Local WP（WordPress 本機開發環境）MySQL 資料庫**的全端本機工具：串接 **Gemini API** 做逐段日文校對、串接 **Claude Code skill** 做事實查核，並管理審核進度。日文校對以 **H2 段落**為單位交給 AI（可選「微調」或「段落重寫」），事實查核以 HTML 文字節點為單位；經過人工審核後才覆蓋回資料庫，覆蓋前自動備份，確保修改全程可控、可回溯。

> **開發動機**：我是一個學習日文的外國人，仍然用日文寫部落格記錄生活與旅遊資訊。市面上的 AI 校正工具常會把文字「修正」成教科書式的標準日文，抹去台灣人寫日文特有的語感、口語、顏文字；因此我自己寫了這個工具，讓 AI 只挑出真正的文法／用字錯誤，同時保留自己原本的寫作風格。

## 三種模式

網頁左側有三個分頁，各自獨立、互不影響：

![style-editor 畫面預覽](./images/preview.png)

### 📝 日文校對

用 Gemini 依照你的寫作風格校正日文、檢查/建議標題。文章會以 **H2 段落**為單位處理，每一段整段決定「採用」或「維持原文」，全部審核完後才會覆蓋回 WordPress 資料庫的原文章。

有兩種模式，開始校對前先選整篇的預設模式，審查時每一段也可以單獨改用另一種模式重跑：

| 模式 | 適合 | AI 做什麼 | 畫面呈現 |
| ---- | ---- | --------- | -------- |
| **微調** | 熟悉的領域，只需要小修 | 只改錯字、活用、助詞、表記等，段落數量和順序不變 | 原文上直接標刪除線／新字 |
| **段落重寫** | 不熟的領域，句子順序需要整個調整 | 在段落群組內重排句子、合併或拆開句子與段落 | 原文和改寫後左右並排，附一句改寫說明 |

段落重寫時，圖片、內嵌、Cocoon 方塊、H3 小標、有樣式的段落都**固定不動**（裡面的文字只做微調），AI 只能在兩個固定元素之間重排文字，不會把某張圖的說明搬到另一張圖下面。粗體、連結、顏色等格式會跟著句子一起移動。

- 只挑「真正的錯誤」修正：錯字、活用錯誤（例如「楽しいでした」→「楽しかったです」）、看不懂意思的助詞問題等。
- **不會**把你的日文改成教科書式的標準日文。台灣人寫日文特有的語感、口語、顏文字、等都會保留。
  這份判斷邏輯寫在 [`style_profile.md`](./style_profile.md)，是根據你現有文章分析出來的，**可以直接編輯這個檔案**來調整 AI 的判斷標準（也包含標題風格）。
- 讀完全文後會檢查標題文法是否有問題；如果標題本身沒問題、也想不到更好的寫法，就不會硬湊 3 個建議。
  只要文法有問題，或有更符合你風格的寫法，才會給你剛好 3 個標題建議，你可以選要用哪一個（或維持原標題）。
- 覆蓋原文前一定會自動備份（標題+內文）到 `style-editor/backups/`，可以隨時找回原始內容。
- 覆蓋前會檢查文章的內容或標題是否在 WordPress 後台被改過，如果有改過會提醒你重新校對，不會誤蓋掉你手動的修改。

詳細操作步驟見下方「日文校對：詳細操作步驟」。

### 🔍 事實查核

這個分頁**不會呼叫任何 AI**，單純把文章內容匯出成一個檔案（`style-editor/factcheck_exports/{文章ID}.json`）。

- 按「開始查核」之後，畫面只會告訴你檔案匯出到哪裡，接下來要**自己到 Cowork 對話請 Claude 查核這篇文章**（例如「幫我查核文章 ID 6809」）。
- 實際的查核規則、輸出格式寫在 [`.claude/skills/blog-factcheck/SKILL.md`](./.claude/skills/blog-factcheck/SKILL.md)。這是**專案層級的 skill**：只要你在 `style-editor` 這個專案資料夾裡開 Claude Code，就會自動偵測到。
- 查完後，查核結果由 Claude 直接寫回 `style-editor/sessions/factcheck/{文章ID}.json`——回到這個網頁重新整理，就會在對應段落旁看到查核筆記。
- **為什麼不像日文校對一樣直接串 API，要手動貼給 Claude？** 事實查核比日文文法校正更吃「上網查證＋判斷資訊可信度」的能力，這塊 Claude 明顯比 Gemini 強；但直接在程式裡串 Claude API 要另外付費，所以退而求其次，借用你原本就在用的 Claude（寫成一個 skill 讓查核流程固定下來），而不是在這支工具裡整合一組要花錢的 API。
- 這是「筆記功能」，沒有採用/維持原文的按鈕，也**不會自動套用回 WordPress**——查核結果只給你自己看，看完覺得要改，自己手動編輯文章即可。

### 🗂️ 草稿管理

列出目前所有校對／查核產生的草稿進度（不分種類），每列有流水編號，方便看總數。可以看狀態、看時間，直接刪除單一份，或勾選多份（表頭的勾選框可以全選）後按「刪除選取」批次刪除。這裡的刪除只會清掉本機的審核進度檔案，不會動到 WordPress 資料庫裡的文章本身。

## 安裝

前提：Local WP 要開著（MySQL 才會啟動）。

```powershell
cd "<你的部落格專案資料夾>\style-editor"
pip install -r requirements.txt --break-system-packages
```

如果你的環境不需要 `--break-system-packages`，拿掉即可。

## 設定 API Key（Gemini，免費）

到 https://aistudio.google.com/apikey 用 Google 帳號登入，建立一組免費的 Gemini API Key。

複製 [`​.env.example`](./.env.example) 到**上一層**（你的部落格專案根目錄），改名成 `.env`：

```powershell
cp .env.example ../.env
```

打開 `<你的部落格專案資料夾>\.env`，把 `GEMINI_API_KEY` 改成你的 Key：

```
GEMINI_API_KEY=AIzaSy........
```

**目前使用的模型**：`gemini-3.5-flash-lite`（2026 年 9 月改用，原因見下方「段落、節點與流量限制」的背景說明——免費額度比 `gemini-3.5-flash` 大上不少）。
如果你之後發現免費額度用完跳錯誤，可以把 `.env` 裡的 `GEMINI_MODEL` 換成其他型號（例如更早期的 `gemini-3.1-flash-lite`）。
免費帳號的實際額度可能會隨時間調整，可以到 https://aistudio.google.com/rate-limit 查看目前帳號的即時額度。

DB 連線資訊會直接沿用同一個 `.env`（跟 `sync-analytics.py` 共用），不用重新設定。

## 日文校對：詳細操作步驟

1. 左側清單選一篇文章。
2. 在右上角選模式：**微調**（熟悉的領域）或 **段落重寫**（不熟的領域，需要調整句子順序）。會記住你上次選的模式。
3. 按「開始 / 重新 AI 校對」，AI 會同時做兩件事（一段打一次 API，文章越長越久）：
    - 一段一段校正內文
    - 讀完全文後檢查標題，視情況給出標題建議
4. **標題區**：文字下方會顯示標題文法檢查結果。如果有建議，會列出「維持原標題」+ 最多 3 個新標題，用單選鈕選你想用的那個（預設維持原標題）。
5. **內文區**：每個 H2 段落是一張卡片，標題列有段落編號、模式、修改狀態和按鈕：
    - ✓ 採用：這一段整段採用 AI 的修改（預設）
    - ✕ 維持原文：這一段整段不採用
    - ✎ 重新調整：輸入意見（例如「這太生硬了」「結論請放在最前面」），AI 會參考上一次的結果，重新處理這一段
    - 改用段落重寫重跑／改用微調重跑：這一段換成另一種模式，從原文重新處理
    - 微調的卡片：綠色底線是建議的修改，紅色刪除線是原文（為了好讀，這裡只顯示文字，粗體等格式不會顯示，但套用時會保留）。
    - 段落重寫的卡片：左邊原文、右邊改寫後，上方紫色框是 AI 的改寫說明。段落重寫的改動比較大，建議逐段對照確認意思沒有被改掉。
    - 如果某段出現橘色警告，代表 AI 回傳的內容沒通過格式檢查（例如粗體記號不見），那些部分已自動保留原文，可以按「重新調整」再試一次。
6. 都確認好之後，按右上角「套用並覆蓋原文」。文章內容（以及你選的標題，如果不是原標題）會被覆蓋，原始版本自動備份在 `style-editor/backups/`。沒有修改或維持原文的段落，會一個字元都不變地保留。
7. 你可以隨時關掉瀏覽器，之後重新打開網頁、選同一篇文章，進度會留著（存在 `style-editor/sessions/`，未套用前不會影響 WordPress）。

> 2026 年 11 月以前產生的日文校對草稿是舊版「逐處審查」格式，新版讀不了，畫面會提示重新校對；舊草稿可以在「草稿管理」刪掉。

## 找回備份

`style-editor/backups/{文章ID}-{網址代稱}-{時間戳記}.json` 是覆蓋前的原始 `{title, content}`。
如果想復原，打開 Local WP 的 phpMyAdmin / Adminer，把該文章 `wp_posts.post_title` / `post_content` 欄位貼回備份檔對應的內容即可。

## 已知限制

- 日文校對的採用／維持原文是以整個 H2 段落為單位，不能只採用段落裡的其中一處修改；不同意的地方請用「✎ 重新調整」告訴 AI。
- 段落重寫模式下，AI 只能在兩個固定元素（圖片、H3、方塊等）之間重排文字；文字要跨過圖片移動的話，請自己在 WordPress 調整。
- 段落重寫時如果把段落合併或拆開，新段落一律是沒有樣式的一般段落（有樣式的段落本來就不參與段落重寫，所以不會遺失樣式）。
- 目前只處理內文和標題，不會校對 SEO meta、分類名稱等其他欄位。
- 沒有實作使用者登入，僅供你自己在本機使用，不要對外開放這個網頁（例如不要用 ngrok 之類的工具公開）。
- Gemini 免費額度有限（依模型而異，請求數/分鐘、請求數/天都有上限），長文章或短時間內連續校對多篇可能會撞到限制，出現錯誤訊息時稍等一下再試即可。細節見下方「段落、節點與流量限制」。

## 段落、節點與流量限制（技術筆記）

### 背景：為什麼會有這些對策

2026 年 9 月，當時用的模型是 `gemini-3.5-flash`，免費額度是 **RPM 5、TPM 250K、RPD 20**（在
https://aistudio.google.com/rate-limit 查到的即時數字）。其中 RPD（每日請求數）只有 20 次、而且是整個
API 專案共用，實際使用時很快就撞到，因此下面「目前的對策」列的
批次打包、每分鐘節流、429 重試、輸出上限這幾個機制，都是針對那個當下的額度做的因應。

2026 年 9 月 12 日改用 `gemini-3.5-flash-lite` 之後，同一個帳號查到的免費額度變成 **RPM 15、TPM 250K、
RPD 500**——RPD 從 20 提升到 500（25 倍），RPM 從 5 提升到 15（3 倍）。原本最容易先卡住的 RPD 瓶頸，
正常使用下應該不會再遇到。`GEMINI_RPM_LIMIT` 的預設值已經跟著改成 15；批次打包、429 重試這些機制則
**沒有拿掉**，繼續當防呆保留著（額度還是有限，只是變寬鬆）。

### 日文校對：以 H2 段落為單位（`section_diff.py`）

2026 年 11 月起，日文校對不再用文字節點，而是以 **H2 段落**為單位：第 0 段是第一個 H2 之前的開頭，之後每個 H2 加上它底下的內容各是一段。原因是文字節點太碎（同一句話被粗體、連結切成好幾塊），AI 只看得到半句話，只能改用字，沒辦法調整句子順序。

處理流程：

1. **切段**：文章是 Gutenberg 區塊（`<!-- wp:paragraph -->` 這種註解包起來的區塊），先切出最外層的區塊，再以最外層的 H2 標題區塊為界切成段落。
2. **分類**：一般段落（沒有樣式的 `<p>`）可以段落重寫，相鄰的一般段落組成一個「群組」；圖片、H3、有樣式的段落、Cocoon 方塊、清單等是固定元素，位置不動，裡面的文字只做微調。
3. **記號**：`<strong>`、`<a>`、`<span>` 等內嵌標籤換成成對的 `⟦T1⟧…⟦/T1⟧`，`<br>` 換成 `⟦T2/⟧`，簡碼換成 `⟦S3⟧`。AI 重排句子時，記號會跟著句子一起移動。
4. **驗證**：AI 回傳後，檢查每個記號是否剛好出現一次、成對且在同一段落、沒有出現新的 HTML 標籤；微調模式還會檢查段落數量沒變。不合格的部分自動重試 1 次，還是不行就保留原文並在畫面上顯示警告。AI 很容易把「～」換成長得很像的「〜」、把「...」換成「…」，這個由程式自動換回原文的寫法。
5. **組回**：沒有修改的部分直接用原始字串（一個字元都不變），有修改的部分才局部替換；段落重寫過的群組重新包成 `<!-- wp:paragraph --><p>…</p><!-- /wp:paragraph -->`。

一篇文章大約 5～8 個 H2 段落（目前 201 篇文章平均約 6.4 段，最長的一段約 3,200 字），一段打一次 API，再加 1 次標題建議，總請求數大約 **6～9 次**，低於 `GEMINI_RPM_LIMIT`（預設 15），正常情況下按一次「開始／重新」就會整篇跑完。超過 15 段的長文，會進到「已完成 X/Y 段，請稍等再按一次」的分段續跑流程。

段落重寫需要比較強的重組能力，如果 `gemini-3.5-flash-lite` 的段落重寫效果不夠好，可以在 `.env` 設定 `GEMINI_REWRITE_MODEL`，只讓段落重寫模式改用比較強的模型（微調和標題建議還是用 `GEMINI_MODEL`）。

### 事實查核：以「節點」為單位（`html_diff.py`）

事實查核仍然用 `html_diff.py` 的 `extract_nodes` 把文章 HTML 拆成一個一個「節點」。**節點的單位是「一段連續文字」（HTML 的文字節點），不是一整個段落**：同一個 `<p>` 段落裡如果有 `<strong>`、`<a>` 這類內嵌標籤，標籤前後的文字會被切成好幾個獨立節點。匯出給 Claude 的 `factcheck_exports/{post_id}.json` 和 Claude 寫回的 `sessions/factcheck/{post_id}.json` 都是這個格式，blog-factcheck skill 依賴它，所以沒有跟著改。

### 什麼是「限流」

Gemini 免費方案有三種額度，各自獨立計算：

| 名稱                       | 意思                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------- |
| RPM（Requests Per Minute） | 每分鐘最多打幾次 API                                                                |
| TPM（Tokens Per Minute）   | 每分鐘最多處理幾個詞元，通常額度很大、不太會卡到                                    |
| RPD（Requests Per Day）    | 一整天最多打幾次 API，這個 API 專案下所有用量共用（不分文章），常常是最先卡住的一個 |

RPD 特別容易先被卡住，因為它算的是「次數」而不是「內容量」，就算一次塞很多文字進去也只算一次請求。

### 目前的對策

1. **以段落為單位（省 RPM / RPD）**：一個 H2 段落打一次 API，請求次數跟段落數量一樣，不會因為排版裡的粗體、連結多就變多。（舊版的 `CORRECTION_BATCH_SIZE` 已經不再使用。）
2. **每分鐘節流**：
    - `app.py` 一次「開始/重新校對」最多只打 `GEMINI_RPM_LIMIT`（預設 15）次 API（含格式驗證失敗的重試），打完就先停下來、把進度存檔，等使用者下次再按繼續。
    - `ai_corrector.py` 的 `_throttle()` 是最後一道防線，確保過去 60 秒內送出的請求數不超過 `GEMINI_RPM_LIMIT`。
3. **429 自動重試**：`ai_corrector.py` 的 `_generate_with_retry` 撞到 429（額度超過）時，會讀 Gemini 回傳的建議等待秒數，重試最多 `GEMINI_MAX_RETRIES`（預設 3）次。**這個機制是設計給「撞到 RPM」用的**——如果是 RPD（每日額度）用完，重試也沒用，要等隔天額度重置才會恢復，這種情況下畫面上「請稍等一下再試」的訊息會不準。
4. **輸出上限**：`ai_corrector.py` 裡 `SECTION_MAX_OUTPUT_TOKENS`（預設 12000）限制了段落校正單次回應最多能回多少詞元。段落校正會回傳整段修正後的全文，萬一回應被截斷，JSON 會解析失敗，這段會顯示「AI 處理失敗、保留原文」，不會套用半截的內容。
