# 日文校對工具（style-editor）

**繁體中文** | [English](README.en.md)

直接讀取 **Local WP（WordPress 本機開發環境）MySQL 資料庫**的全端本機工具：串接 **Gemini API** 做逐段日文校對、串接 **Claude Code skill** 做事實查核，並管理審核進度。文章會被拆成 HTML 文字節點交給 AI 逐段建議修改，經過「採用／維持原文／要求重寫」的人工審核後才覆蓋回資料庫，覆蓋前自動備份，確保修改全程可控、可回溯。

> **開發動機**：我是一個學習日文的外國人，仍然用日文寫部落格記錄生活與旅遊資訊。市面上的 AI 校正工具常會把文字「修正」成教科書式的標準日文，抹去台灣人寫日文特有的語感、口語、顏文字；因此我自己寫了這個工具，讓 AI 只挑出真正的文法／用字錯誤，同時保留自己原本的寫作風格。

## 三種模式

網頁左側有三個分頁，各自獨立、互不影響：

![style-editor 畫面預覽](./images/preview.png)

### 📝 日文校對

用 Gemini 依照你的寫作風格校正日文、檢查/建議標題，網頁上逐條標記修改處，全部審核完後才會覆蓋回 WordPress 資料庫的原文章。

- 只挑「真正的錯誤」修正：錯字、活用錯誤（例如「楽しいでした」→「楽しかったです」）、看不懂意思的助詞問題等。
- **不會**把你的日文改成教科書式的標準日文。台灣人寫日文特有的語感、口語、顏文字、等都會保留。
  這份判斷邏輯寫在 [`style_profile.md`](./style_profile.md)，是根據你現有文章分析出來的，**可以直接編輯這個檔案**來調整 AI 的判斷標準（也包含標題風格）。
- 讀完全文後會檢查標題文法是否有問題；如果標題本身沒問題、也想不到更好的寫法，就不會硬湊 3 個建議。
  只要文法有問題，或有更符合你風格的寫法，才會給你剛好 3 個標題建議，你可以選要用哪一個（或維持原標題）。
- 覆蓋原文前一定會自動備份（標題+內文）到 `style-editor/backups/`，可以隨時找回原始內容。
- 覆蓋前會檢查文章的內容或標題是否在 WordPress 後台被改過，如果有改過會提醒你重新校對，不會誤蓋掉你手動的修改。

詳細操作步驟見下方「日文校對：詳細操作步驟」。

### 🔍 事實查核

這個分頁**不會呼叫任何 AI**，單純把文章內容匯出成一個檔案（`style-editor/factcheck_exports/{文章ID}.json`）。

- 按「開始查核」之後，畫面只會告訴你檔案匯出到哪裡，接下來要**自己到 Cowork 對話請 Claude 查核這篇文章**（例如「幫我查核文章 ID 6809」）。
- 實際的查核規則、輸出格式寫在 [`.claude/skills/blog-factcheck/SKILL.md`](./.claude/skills/blog-factcheck/SKILL.md)。這是**專案層級的 skill**：只要你在 `style-editor` 這個專案資料夾裡開 Claude Code，就會自動偵測到。
- 查完後，查核結果由 Claude 直接寫回 `style-editor/sessions/factcheck/{文章ID}.json`——回到這個網頁重新整理，就會在對應段落旁看到查核筆記。
- **為什麼不像日文校對一樣直接串 API，要手動貼給 Claude？** 事實查核比日文文法校正更吃「上網查證＋判斷資訊可信度」的能力，這塊 Claude 明顯比 Gemini 強；但直接在程式裡串 Claude API 要另外付費，所以退而求其次，借用你原本就在用的 Claude（寫成一個 skill 讓查核流程固定下來），而不是在這支工具裡整合一組要花錢的 API。
- 這是「筆記功能」，沒有採用/維持原文的按鈕，也**不會自動套用回 WordPress**——查核結果只給你自己看，看完覺得要改，自己手動編輯文章即可。

### 🗂️ 草稿管理

列出目前所有校對／查核產生的草稿進度（不分種類），可以看狀態、看時間，或直接刪除不需要的草稿。這裡的刪除只會清掉本機的審核進度檔案，不會動到 WordPress 資料庫裡的文章本身。

## 安裝

前提：Local WP 要開著（MySQL 才會啟動）。

```powershell
cd "<你的部落格專案資料夾>\style-editor"
pip install -r requirements.txt --break-system-packages
```

如果你的環境不需要 `--break-system-packages`，拿掉即可。

## 設定 API Key（Gemini，免費）

到 https://aistudio.google.com/apikey 用 Google 帳號登入，建立一組免費的 Gemini API Key。

複製 [`​.env.example`](./.env.example) 到**上一層**（你的部落格專案根目錄），改名成 `.env`：

```powershell
cp .env.example ../.env
```

打開 `<你的部落格專案資料夾>\.env`，把 `GEMINI_API_KEY` 改成你的 Key：

```
GEMINI_API_KEY=AIzaSy........
```

**目前使用的模型**：`gemini-3.5-flash-lite`（2026 年 9 月改用，原因見下方「節點與流量限制」的背景說明——免費額度比 `gemini-3.5-flash` 大上不少）。
如果你之後發現免費額度用完跳錯誤，可以把 `.env` 裡的 `GEMINI_MODEL` 換成其他型號（例如更早期的 `gemini-3.1-flash-lite`）。
免費帳號的實際額度可能會隨時間調整，可以到 https://aistudio.google.com/rate-limit 查看目前帳號的即時額度。

DB 連線資訊會直接沿用同一個 `.env`（跟 `sync-analytics.py` 共用），不用重新設定。

## 執行

```powershell
cd "<你的部落格專案資料夾>\style-editor"
python app.py
```

瀏覽器打開 http://localhost:5055

## 日文校對：詳細操作步驟

1. 左側清單選一篇文章。
2. 按「開始 / 重新 AI 校對」，AI 會同時做兩件事（文章越長越久）：
    - 校正內文文字
    - 讀完全文後檢查標題，視情況給出標題建議
3. **標題區**：文字下方會顯示標題文法檢查結果。如果有建議，會列出「維持原標題」+ 最多 3 個新標題，用單選鈕選你想用的那個（預設維持原標題）。
4. **內文區**：綠色底線是建議的修改，紅色刪除線是原文。滑鼠移到修改處會出現三個小按鈕：
    - ✓ 採用這個修改
    - ✕ 維持原文，不採用
    - ✎ 不滿意，輸入意見要求 AI 重新調整這一段（例如「這太生硬了」「這不是錯字」）
    - 每個修改預設是「採用」狀態，你只需要處理你不同意的地方即可。
5. 都確認好之後，按右上角「套用並覆蓋原文」。文章內容（以及你選的標題，如果不是原標題）會被覆蓋，原始版本自動備份在 `style-editor/backups/`。
6. 你可以隨時關掉瀏覽器，之後重新打開網頁、選同一篇文章，進度會留著（存在 `style-editor/sessions/`，未套用前不會影響 WordPress）。

## 找回備份

`style-editor/backups/{文章ID}-{網址代稱}-{時間戳記}.json` 是覆蓋前的原始 `{title, content}`。
如果想復原，打開 Local WP 的 phpMyAdmin / Adminer，把該文章 `wp_posts.post_title` / `post_content` 欄位貼回備份檔對應的內容即可。

## 已知限制

- 「✎ 重新調整」會把整個段落（同一個文字節點）重新校正一次，不是只改單一個字詞，如果段落內有多處修改，會一起重新產生。
- 目前只處理內文文字節點和標題，不會校對 SEO meta、分類名稱等其他欄位。
- 沒有實作使用者登入，僅供你自己在本機使用，不要對外開放這個網頁（例如不要用 ngrok 之類的工具公開）。
- Gemini 免費額度有限（依模型而異，請求數/分鐘、請求數/天都有上限），長文章或短時間內連續校對多篇可能會撞到限制，出現錯誤訊息時稍等一下再試即可。細節見下方「節點與流量限制」。

## 節點與流量限制（技術筆記）

### 背景：為什麼會有這些對策

2026 年 9 月，當時用的模型是 `gemini-3.5-flash`，免費額度是 **RPM 5、TPM 250K、RPD 20**（在
https://aistudio.google.com/rate-limit 查到的即時數字）。其中 RPD（每日請求數）只有 20 次、而且是整個
API 專案共用，實際使用時很快就撞到，因此下面「目前的對策」列的
批次打包、每分鐘節流、429 重試、輸出上限這幾個機制，都是針對那個當下的額度做的因應。

2026 年 9 月 12 日改用 `gemini-3.5-flash-lite` 之後，同一個帳號查到的免費額度變成 **RPM 15、TPM 250K、
RPD 500**——RPD 從 20 提升到 500（25 倍），RPM 從 5 提升到 15（3 倍）。原本最容易先卡住的 RPD 瓶頸，
正常使用下應該不會再遇到。`GEMINI_RPM_LIMIT` 的預設值已經跟著改成 15；批次打包、429 重試這些機制則
**沒有拿掉**，繼續當防呆保留著（額度還是有限，只是變寬鬆）。

### 什麼是「節點」

此專案不是把整篇文章當一大塊文字丟給 Gemini，而是先用 `html_diff.py` 的 `extract_nodes` 把文章 HTML 拆成一個一個「節點」。**節點的單位是「一段連續文字」（HTML 的文字節點），不是一整個段落**：同一個 `<p>` 段落裡如果有 `<strong>`、`<a>` 這類內嵌標籤，標籤前後的文字會被切成好幾個獨立節點，不會合併成一個。每個節點送給 AI 之前，會用 `⟦N0⟧...⟦/N0⟧` 這種標籤包起來，讓 AI 回傳時可以照原本的編號一一對應回去。

這樣拆的好處：

- 可以「逐段」記錄狀態（`corrected: True`/`False`），中途中斷或撞到流量限制時，已經校正好的段落不用重打。
- 畫面上可以針對單一段落做「採用／維持原文／重新調整」，而不是整篇文章一次全部套用或全部重來。

### 舉例：一篇 3000 字的文章會切成幾個節點、打幾次請求

因為節點是照「文字節點」切的（見上面），**節點數量主要看排版裡用了多少內嵌標籤（`<strong>`、`<a>` 等），不是單純看字數**。同樣 3000 字，排版越花俏，節點數越多。舉兩個情境：

- **幾乎沒有內嵌標籤**（例如 3 個 `<h2>` 小標 + 10 個 `<p>` 段落 + 1 個 4 項的清單，段落內文字都連續、沒有粗體/連結穿插）：大約 **17 個節點**（3 + 10 + 4）。
- **常見的 Cocoon 部落格排版**（段落中間夾雜粗體強調、站內連結，平均每段被切成 1.5～2 個文字節點）：同樣的結構可能變成 **25～35 個節點**。

以 `CORRECTION_BATCH_SIZE`（預設 12）換算成請求次數（`ceil(節點數 / 12)`，再加 1 次標題建議）：

| 節點數 | 內文校正批次數  | + 標題建議 | 總請求數 |
| ------ | --------------- | ---------- | -------- |
| 17     | ceil(17/12) = 2 | +1         | **3 次** |
| 30     | ceil(30/12) = 3 | +1         | **4 次** |

兩種情況都遠低於 `GEMINI_RPM_LIMIT`（預設 15），所以正常情況下按一次「開始／重新」就會整篇跑完，不會進到「已完成 X/Y 段，請稍等再按一次」那個分段續跑的流程。真的會需要分好幾次按的，通常是文章特別長（節點數上看百來個）、或當天額度已經被別篇文章用掉一部分。

### 什麼是「限流」

Gemini 免費方案有三種額度，各自獨立計算：

| 名稱                       | 意思                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------- |
| RPM（Requests Per Minute） | 每分鐘最多打幾次 API                                                                |
| TPM（Tokens Per Minute）   | 每分鐘最多處理幾個詞元，通常額度很大、不太會卡到                                    |
| RPD（Requests Per Day）    | 一整天最多打幾次 API，這個 API 專案下所有用量共用（不分文章），常常是最先卡住的一個 |

RPD 特別容易先被卡住，因為它算的是「次數」而不是「內容量」，就算一次塞很多文字進去也只算一次請求。

### 目前的對策

1. **批次打包（省 RPM / RPD）**：不是一個節點打一次 API，而是把 `CORRECTION_BATCH_SIZE`（`.env`，預設 12）個節點包成一批，一次 API 呼叫校正一整批。節點數量固定時，批次開越大，總共要打的請求次數越少。
2. **每分鐘節流**：
    - `app.py` 一次「開始/重新校對」最多只送出 `GEMINI_RPM_LIMIT`（預設 15）批，送完就先停下來、把進度存檔，等使用者下次再按繼續。
    - `ai_corrector.py` 的 `_throttle()` 是最後一道防線，確保過去 60 秒內送出的請求數不超過 `GEMINI_RPM_LIMIT`。
3. **429 自動重試**：`ai_corrector.py` 的 `_generate_with_retry` 撞到 429（額度超過）時，會讀 Gemini 回傳的建議等待秒數，重試最多 `GEMINI_MAX_RETRIES`（預設 3）次。**這個機制是設計給「撞到 RPM」用的**——如果是 RPD（每日額度）用完，重試也沒用，要等隔天額度重置才會恢復，這種情況下畫面上「請稍等一下再試」的訊息會不準。
4. **輸出上限跟批次大小連動**：`ai_corrector.py` 裡 `BATCH_MAX_OUTPUT_TOKENS`（預設 8000）限制了批次校正單次回應最多能回多少詞元。因為批次校正是把**整批節點修正後的全文**都 echo 回來（不是只回差異），把 `CORRECTION_BATCH_SIZE` 調大時，如果這批文字量超過這個上限，AI 的回應會被截斷——被截斷的節點會被程式當成「沒有修改」直接保留原文，畫面上不會顯示錯誤，只會看起來像「這段沒被改到」。調大批次大小時，這個常數要一起往上調。
